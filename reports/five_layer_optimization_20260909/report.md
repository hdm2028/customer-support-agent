# 五层评测优化与复测

已完成本轮有 Trace 支持的修复、固定响应回放、整链路复测和隔离代码检查。RAG 与政策咨询有改善，原通过案例无新增失败，禁止工具调用为 0。**尚未达到全部业务验收通过，不能声称项目已优化完成或可以自动上线。** 投诉语义、003 召回，以及旧业务断言和夹具隔离问题仍待解决。

## 实现与取舍

1. **查询路由容错**：`app/agent/routing/llm_router.py` 新增可关闭的辅助主题清理。合法主意图、动作、主题仍走原校验；仅 query 可丢弃非法 related_topics 字符串，并在 SemanticRoute 中记录 ignored_related_topics。非法主字段、非法数组类型、execute/handoff 保持严格拒绝。不将未知主题映射成退款动作，不新增模型调用。
2. **实际政策工具接入互补证据**：五层 runner 增加 `--profile optimized`，显式使用项目已有互补选择器，并在政策工具中启用已有完整上下文桥接与 Top20→Top5 选择。没有换模型、改召回权重、改知识内容、修改分块；没有重新研发一个以 expected 为特征的选择器。默认 baseline 和生产 `.env` 不变。
3. **回答否定句独立诊断**：新增 `scripts/eval/negation_aware_answer.py`，对每次禁词命中检查明确局部否定。双重否定、疑问句、条件句、引语继续保守判定。它只产生新报告，原 Answer evaluator、原标签、原分数和质量门禁都保留。

第一版曾允许所有动作丢弃非法辅助主题，固定回放和 live_b 都出现一条禁止工具调用：投诉退款请求恢复成投诉执行，额外创建工单。该版本已否决。最终限制为 query，`frozen_final` 和 `live_final` 均恢复为 0；原试验产物仍保留，没有隐藏这次回退。

## 对照条件与成本

- 最终复测使用冻结源码副本、独立 SQLite、进程内缓存、本地知识副本。六份 Dev 数据、知识文件及 orders.json 与 A 字节相同；最终运行期间源码未变。未读 validation/final_test 或按 Holdout 失败调参。未写生产库或生产索引。
- 固定 `glm-4-flash`、temperature=0.2、fixed_256 / overlap 32、local_hash_v1 / 256、hybrid_rule、召回权重 0.62/0.28/0.10。模型未更换。
- 独立 RAG 全部 26 案的完整有序候选记录、查询与 KB 版本相同，均为 candidate_k=20 / top_k=5。政策工具从默认 Top2 接入已有 Top5 桥接，因此不能把 Answer/E2E 变化宣称为“同样两条证据下生成能力变强”。
- 业务 evaluator 是套件级数据库隔离，尚未按案例隔离或冻结业务时钟；固定日期订单已过退货期限。A/B 业务对照存在此限制，完整运行不等于已恢复完备的可信业务基线。
- RAG 平均检索与选择耗时：V1 4.16→18.13 ms；V2 5.63→34.45 ms。是一次本地运行测量，不是性能压测。
- Trace 中请求平均耗时：Answer 6.72→9.96 s，E2E 5.25→5.87 s；工具层 5.73→5.30 s。网络与模型波动存在，不据此声称工具优化提速。
- 已记录 provider token：Answer 15,643→24,039，E2E 45,472→60,151；全部 Trace 汇总 185,839→208,891。最终有 62 次已记录模型调用，另有 24 次直接 Routing 调用缺 provider usage，因此 token 汇总不是完整账单。所有已观察调用均无依赖失败。不能把未知用量记作 0。

## 验证、回退与停止点

最终源码检查见 [release_final/manifest.json](release_final/manifest.json) 和 [测试日志](release_final/unit_integration.txt)：**296 passed、11 skipped、83 subtests passed**，编译检查通过。11 项跳过仍保留，不算通过；本轮没有重新验证外部 MySQL/Redis/支付接入。测试覆盖非法辅助主题、执行/转人工拒绝、合法写语义保留、政策证据桥接、否定句与混合承诺。整链路评测运行完成，但 `--fail-on-quality` 仍返回 1，原质量门禁没有放宽。

可用 `--profile optimized` 重现实验；省略该参数或使用 `--profile baseline` 回到对照。生产默认和 `.env` 未自动替换。评测配置及否定句诊断用法见 [运行文档](../../docs/five_layer_evaluation.md)。运行配置变更之外，最终业务代码只增加查询辅助主题容错及其结果记录。

剩余问题已逐案核对在 [remaining_contracts.md](remaining_contracts.md)：两个投诉语义失败、RAG 003 召回缺口，以及预期拒绝/工具序列/字面回复/日期和案例共享状态的验收冲突。它们没有被删除、改写标签或补算成通过。下一步需要分别处理语义识别、召回和版本化业务验收；本轮收益不足以自动替换默认方案。

## 未采用的附加语义实验

针对投诉语义错误，又完整运行了一次通用提示词范围修正，强调否定只针对被否定的动作、退款与投诉的主次关系和合法 topic 集合。未加入 case_id 或具体问句特例；全部六套 Dev 数据均测试，见 [action_scope_v2/summary.json](action_scope_v2/summary.json) 与 [逐案对照](comparison_scope_v2.json)。

它让 Tool 从保留版本的 43/55 增至 44/55，恢复 tool_boundary_complaint_refund；但 Routing 的 intent_accuracy 和 route_accuracy 均从 1.0000 降至 0.9583，E2E risk_success_rate 从 0.7143 降至 0.5714。Routing 总通过数仍是 23/24、E2E 仍是 7/12，说明只看整案通过数会漏掉退化。

因此该方案没有采用。三处相关源码已恢复到保留版本，工作区全部 207 个发布检查输入与 `release_final` 中通过测试的源码字节一致，见 [accepted_source_verification.json](accepted_source_verification.json)。失败方案只保存在实验快照中。最终可 review 的本轮代码补丁是 [implementation.patch](implementation.patch)。没有继续尝试多组提示词追分，也没有自动修改旧业务标签。
