# 退款人工审核去重与并发创建

修复了尚未产生退款申请时，重复请求仍新增退款审核单的问题。修改前实际复现：顺序重复创建得到不同审核 ID，四线程首次创建得到 4 个审核单，已有审核批准并创建退款后仍能再创建审核。

同一订单的退款审核创建现在由订单行锁串行处理。已有待审核单则返回原编号，保留原始诉求和审核上下文；审核已批准且存在有效退款时返回退款状态，不伪造新审核编号。原审核被拒绝且未产生退款时，用户的新请求仍可创建新审核。其他审核类型未纳入本轮去重。

编排器识别复用回执后，不再追加自动人工待办或工单。首次请求仍按原流程创建审核及必要人工待办；明确的人工请求仍保留。回复区分“审核单已存在”和“已有退款申请”，不把它们说成新建成功或资金到账。

## 锁与验证

创建过程中锁订单行，读取已有审核时不持有或等待审核行锁，避免与批准路径的“审核→退款→订单”相反。修改前的订单查询用于归属判断，事务中重新读取锁定订单并复核归属。创建失败回滚，不留下去重占位或部分审核记录；没有新增数据库表、索引或迁移。

最终隔离完整检查：**249 项测试、40 个子测试通过**，11 项环境专属测试跳过，3 条已有框架弃用警告。专用 MySQL：**90 项测试、19 个子测试通过**，3 项 SQLite 专属测试跳过，耗时 84.28 秒。

新增验证包括：

- 顺序重复与四线程首次创建只得到一个待审核单。
- 四个独立 MySQL 进程竞争，只一个新建结果、三个复用结果。
- MySQL 固定时序：批准线程持有审核行锁，重复创建线程可完成查询并返回同一审核；释放批准线程后只生成一份退款申请，没有互相等待订单/审核锁。
- 批准后重复请求返回已有退款，拒绝后新请求不被永久拦截，插入故障后可正常重试。
- 同步及 SSE 重复聊天不增加审核或人工工单；模拟过时订单快照后，审核创建检查仍能发现已经批准的退款并正确回复。

首次回归发现原保存失败测试没有准备订单与事务锁夹具，导致在到达注入故障前就退出；已补齐夹具，保留原保存调用次数和失败返回断言。业务复现、首次回归失败及最终通过记录均保留。测试没有调用真实支付渠道。
