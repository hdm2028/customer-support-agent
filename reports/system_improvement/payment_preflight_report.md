# 聊天退款付款前置检查

已将上一阶段的付款条件提前到编排器取得订单事实之后。未付款、付款未确认的退款执行请求不再先进入风控、创建审核或人工待办；保留订单与政策查询，确定性回复说明付款原因、本轮未创建退款/审核，以及取消未支付订单或核实支付的后续路径。显式转人工仍能创建人工待办，付款确认后再次申请仍可进入正常退款流程。

底层退款创建、锁内复核和支付提交检查没有修改。此次前置检查依据本轮订单查询快照，只能减少无效处理；最终资金操作仍依赖底层事务检查。

## 记录语义与对照范围

`refund_decision` 是内部业务决定，采用项目现有 `ticket_decision` 类似的结果记录方式，`success=True/can_create=False` 表示检查成功但不可创建。它没有外部工具调用或依赖失败记录。trace 的 `refund_precondition` 保存付款事实、原计划和生效计划；实际工具调用 trace 仅保留真正执行的工具。

原 evaluator 从 `tool_results` 收集实际工具列表，因此把 `refund_decision` 也计入工具序列，两个工具案例出现额外条目。这个评分现象原样报告，未过滤记录或改 evaluator。成功检查不表示退款成功，回复明确未创建申请。

移除自动人工约束后，原查询构建器不再添加“需要人工处理”上下文，相关政策查询输入随业务计划改变。因此这是固定语义响应的整链路对照，不能称为固定 Top20 的 RAG 对照。没有改召回配置、知识库、分块或默认选择器。

## 验证与产物

完整隔离检查 236 项测试、34 个子测试通过，9 项环境专属测试跳过，3 条已有框架弃用警告。新增检查覆盖未支付/付款未确认的同步与 SSE、禁止最终模型改写业务状态、无业务写入、显式转人工、付款确认后继续执行、政策不可用时保留订单事实判断。

初版测试使用了错误的人工 intent 以及地址政策夹具，修正后再完成修改前复现。新增付款门槛也使两个原风控异常测试的缺失付款字段先被拒绝；已补充已付款订单夹具，保留原风控失败、两次重试上限和不调用退款的断言。失败日志均保留。数据库实现未变，本轮没有重跑此前 MySQL 75 项/13 个子测试和 Redis 6 项，不把本轮 SQLite 检查当成新的 MySQL 故障测试。

B 无真实模型调用，四组回放分别耗时 0.49、3.05、1.46、1.95 秒，仅为本地观测。
