# 人工跟进工单闭环

本阶段补齐原有工单的查询、认领和结案。适用于工具创建的 `pending_human_review` 工单，以及人工审核通过后产生的 `pending_manual_review` 跟进工单。不涉及 RAG、数据标签、召回配置或支付渠道。

## 实现与边界

- `GET /tickets/{ticket_id}`：用户只能查询自己的工单，管理员可以查询全部工单。
- `POST /admin/tickets/{ticket_id}/claim`：管理员认领；状态改为 `in_progress` 并保存操作人。
- `POST /admin/tickets/{ticket_id}/resolve`：只有认领人可以提交结案结果及说明；结果为已核实答复、诉求不予受理或用户撤回，状态为 `resolved`。
- SQLite 事务及 MySQL 行锁保护状态检查和更新；状态与审计记录一起提交。相同认领及相同结案请求可重复提交；不同操作人或不同结案结果不能覆盖已有结果。
- 结案只记录人工跟进结果。不会执行退款、赔付、取消订单，不将工单结案表示为退款完成。真实业务状态仍通过已有业务流程查询或处理。
- 工作台可查看工单诉求、处理进度、认领人和结案说明。管理员可查看工单已保存的审核来源、上下文、政策证据及操作记录；历史工单没有保存的上下文不会补造。普通工具工单目前仍只包含创建时保存的基本字段。

新增测试覆盖审核批准后跟进工单的完整闭环、两种待处理状态、重复请求、未认领结案、他人结案、冲突结果、非法说明、客户越权、缺少身份、HTTP 接口权限及状态码。实际 SQLite/MySQL 均验证 4 线程竞争认领仅一人成功、2 线程竞争结案仅一个结果生效、UPDATE 后注入故障回滚状态及审计。工单并发专项是多连接线程测试，不声称本阶段增加了跨进程工单测试。

工单结案前后订单保持一致，未新建退款或 MQ 消息。前端使用身份版本及当前工单 ID 检查异步响应；文本按 `textContent` 展示。

## 回退及剩余工作

新增工单服务、API、前端和测试可按本阶段修改回退，不涉及表结构或数据迁移。若回退应用，已保存的 `in_progress` / `resolved` 工单仍保留在原 tickets 表，不删除或改回历史状态；旧版不具备继续操作它们的接口。

本阶段完成工单认领和结案。真实支付渠道、生产身份配置、外部人工接管系统与浏览器验收仍待接通；普通工具工单的上下文快照、长期无人处理工单的分页/筛选与转派也尚未补齐。没有运行 validation/final_test，没有扩大 RAG 调参或重新生成案例。
