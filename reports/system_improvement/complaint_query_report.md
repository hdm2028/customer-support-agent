# 投诉查询误触发审核：执行边界修复

当前路由允许 `complaint/query` 触发风控。编排器随后将 `review_required` 升级为 `create_manual_review`，导致只反馈、不要求处理的消息也可能创建审核单。这是已复现的查询到业务写入问题。

本轮仅修改 `decision.py` 的投诉风控条件：投诉的 `execute` 请求才进入这条风控通路。退款、风险执行与审核绕过的原检查保持生效。没有调整模型、提示、知识库、RAG、评分口径或数据标签。

## 复现与验证

修改前新增测试实际复现：普通账号查询多调用风控；高风险账号的同步、流式和多轮首轮查询创建了审核单。旧失败日志保留。修改后这两种账号只查订单，不写工单、审核、退款或消息；真正投诉执行仍风控、审核并创建工单，咨询后再明确执行也能继续处理。

最终隔离完整检查：226 项测试、19 个子测试通过，9 项环境专属测试跳过，3 条已有框架弃用警告。数据库实现没有改动，本轮未重复此前 MySQL 69 项与 Redis 6 项故障测试，也没有以 SQLite 结果替代它们。

## 固定条件 A/B

A 为上一阶段 `address_slots_dev_replay`，B 为 `complaint_query_dev_replay`。四组均采用原开发数据与 evaluator；80 次首轮语义输入和响应逐字相同，全部消费。运行源码快照只差 `app/agent/routing/decision.py`，数据、知识库、演示订单和 evaluator 一致。每组独立数据库、缓存与索引副本，使用原模板回答模式；格式修复和 RAG 实验关闭。

工具选择准确率 0.8364 → 0.8545，危险工具误用计数 4 → 3；工具参数准确率、执行成功率及其他组原标量评分不变。各组均没有通过转失败，不合并总体准确率。

两个实际工具序列改变：

- `tool_contrast_quality_001`：订单查询、风控 → 仅订单查询，纯反馈不再触发原 evaluator 禁止的风控。
- `tool_boundary_complaint_only`：订单查询、风控、审核写入 → 仅订单查询。**该案例仍失败，不能称为业务已完成。** 用户要求投诉处理，但冻结的模型响应为 `query`，上游误判仍存在；本轮遵循查询边界后，原要求的风控、审核、工单都没有执行。原来缺工单，现在缺少更多预期工具，这一业务遗漏没有被不变的失败计数反映出来。后续应解决动作识别，不应恢复查询自动写入来掩盖它。

A/B 均为原响应回放，B 无真实模型调用。B 四组耗时分别 0.48、3.06、1.41、1.86 秒；这是本地运行观测，不能推断真实模型延迟或最终生成质量改善。
