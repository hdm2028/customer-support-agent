# 退款创建与支付提交的付款前置条件

本轮修复资金操作前的确定性缺口：人工批准退款原本要求 `payment_status=paid`，直接退款创建却只排除了 unpaid，支付确认中仍可能通过；已进入处理中的旧退款也可以在订单变为未支付后调用支付适配器。

统一付款检查用于退款资格、实际落库事务和首次支付提交。订单必须明确已支付，且不处于待支付/待付款。创建时锁定并重新读取订单，再在同一事务保存退款与 MQ 事件；首次支付提交按退款行、订单行顺序加锁并核验后记录提交状态。初始订单快照过时也不能绕过落库检查。付款状态拒绝不会标为网络故障，也不会由退款工具要求人工批准来绕过付款条件。

已有资金请求的查询/对账仍可执行，超时后不重复提交。该检查依据本地付款记录，真实渠道付款凭证、验签和实际支付适配仍待接入，不能把它视为真实资金链路验收。

## 测试证据

修改前新增测试实际复现了未确认付款仍创建退款、过时的 paid 快照仍落库、未支付订单的旧退款仍调用测试适配器。使用的都是隔离数据库和 mock 支付适配器，没有真实资金操作。修改前子测试共用同一夹具，首次错误写入可能影响后续子测试；因此不将每条旧失败都解释为独立根因。

修改后检查覆盖未支付、项目实际的 payment_pending、其他未确认状态，拒绝后确认付款可重试、重复申请仍幂等，过时快照的事务内复核，以及付款状态变化后仍可恢复已提交退款的结果。

测试修订均保留记录：三个原故障注入测试将事务替换为 nullcontext，未提供新增订单行锁的夹具，已补充已付款锁定订单；MySQL 本身拒绝 payment_status=NULL，故将缺失/空值状态改为领域输入测试，数据库约束未修改。既有保存故障、响应丢失、MQ 失败断言未删除。

最终隔离全量检查：232 项测试、32 个子测试通过，9 项环境专属测试跳过，3 条已有框架弃用警告。专用 MySQL 检查：75 项测试、13 个子测试通过，3 项 SQLite 专属测试跳过，耗时 65.95 秒。包括原跨进程退款/MQ、审核/撤销、支付恢复和本轮付款边界测试；每项 MySQL 测试使用新 support_test_* 库。见 [检查 manifest](release_checks_refund_payment_final/manifest.json) 和对应 SQLite/MySQL 日志。

未支付和支付确认中的 Dev 请求仍因编排器先进行风控而新增审核/人工待办；已有售后流程的案例仍调用退款工具后才拒绝。这些无效处理尚未解决，不能因底层付款检查通过就称退款前判断已全部完成。下一步应在已取得订单事实后、进入风险审核或退款执行前处理这些业务阻断，并给出确定的原因与可继续路径。

B 无真实模型调用，四组耗时 0.46、2.97、1.41、1.90 秒；这些是本地回放观测，不代表线上延迟或模型质量改善。
