# 语义路由格式修复：不推广

本轮验证了“非法附加主题导致整条语义被丢弃”的实际问题，并完成一次固定首轮模型输出的 A/B。**格式修复成功，但整体通过数没有提高，危险工具误用计数增加，因此保留默认关闭，不作为当前默认方案。**

## 诊断及修改范围

旧记录显示 `answer_refund_004` 因 `related_topics=['return_policy']` 校验失败而回退，原语义原始 JSON 未保存，不能直接重放该次模型输出。此次重新运行固定隔离开发配置，保存原始响应后发现同类问题再次出现：有效的主语义 `return_refund / query / refund_eligibility` 被非法附加主题连带丢弃。

增加可选 `SEMANTIC_ROUTE_REPAIR=once`：首次 JSON 或枚举校验失败后，模型最多修复一次；网络/服务错误不进入格式修复，合法输出不增加调用。修复请求只有原问题、原响应、原提示及实际校验错误，没有 expected 或审核标签。原响应中合法的 intent、action_type、topic 必须保持不变，程序再检查这一点；修复失败继续安全回退。

这项机制不解决合法 JSON 中的语义误判。保留主字段也意味着它不会擅自把已经合法但错误的投诉主意图改成退款主意图。没有改 evaluator、数据 Schema/Validator、评测标签或检索配置。

## A/B 条件及结果

A：关闭修复，真实调用当前 glm-4-flash 路由模型，temperature 0.2。B：逐条复用 A 的全部首轮输入及响应，只对格式错误调用真实模型修复。四组分别使用新 SQLite、固定演示订单和私有知识库副本；模板回答，RAG 实验开关关闭。

80 次首轮响应逐项验证完全一致，B 全部消费，没有重抽正常案例。数据、知识库、订单及原四个 evaluator 文件逐字一致。A/B 配置仅修复开关不同。两份源码快照的差异是修复分支补充主字段保持检查，以及回放工具补充严格消费核对；A 修复开关关闭，这段分支没有运行。A 的外部工作树指纹变化不能当成执行混版：各组均使用运行开始冻结的同一源码快照，实际保护输入已独立核对。

## 运行开销与验证

A 共 80 次真实首轮路由调用；其中工具/回答/端到端的 56 次有 request trace usage，provider 共报告 170,229 tokens。路由 evaluator 的另外 24 次没有 request usage trace，原 manifest 的 trace 汇总显示 0 不能解释为未调用模型，原始响应记录证明调用已发生；不估算这 24 次实际用量。

B 实际修复 3 次，provider 报告 10,255 tokens；修复调用耗时合计 17.5768 秒。其余 80 次是本地原响应回放，没有模型费用。B 总运行时间不能和 A 直接比较来宣称性能提升，因为正常首轮调用被回放替代。

最终隔离全量检查 216 项测试、17 个子测试通过，9 项环境专属测试跳过。新增检查覆盖开关、合法输出不修复、一次修复上限、网络错误不重试、非法修复回退、禁止修改合法主字段，以及回放输入不一致时必须使实验失败。数据库代码未改，本阶段没有重复 MySQL/Redis 故障检查；此前结果仍独立保存。
