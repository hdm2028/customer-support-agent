# 已有退款与订单售后状态的后续处理

修复了两个已复现的问题：已有退款的重复聊天请求仍可能创建新工单；只有订单售后状态时，仍先调用风控和退款工具再拒绝。

订单工具先检查归属，再读取已有有效退款的编号、订单号和状态。查询失败会报告失败并停止后续执行，不把读取失败当作“没有申请”。已有申请直接返回真实状态；只有“退货审核中”等订单状态时，明确本轮未查到有效退款申请，不编造退款编号。初始快照未发现申请、退款工具后来返回幂等回执时，也停止追加工单/审核/自动转人工。付款检查和底层退款幂等机制保持生效。

## 实测

完整隔离检查 **242 项测试、40 个子测试通过**，9 项环境专属测试跳过，3 条已有框架弃用警告。专用 MySQL **81 项测试、19 个子测试通过**，3 项 SQLite 专属测试跳过；每项使用独立 support_test_* 库，耗时 76.46 秒。

新增六项检查覆盖：只有售后标记且没有退款记录；同步/流式重复申请保持退款、消息、审核和工单数量不变；六种已有退款状态的准确表达；过时快照后的幂等回执不追加工单；跨用户访问在读取退款信息前被拒绝；读取退款失败时不继续创建。状态表达测试注入数据库状态，不是实际渠道支付测试。首次失败日志保留，两个新读取接口测试在修改前因接口尚不存在而失败，不将它们算作旧代码业务缺陷复现。

订单工具新增一次已有退款查询，输出仅含必要的状态摘要，没有修改订单持久化数据。该读操作进入既有工具超时/重试范围。此次未测高并发数据库负载，不宣称额外查询零开销。
