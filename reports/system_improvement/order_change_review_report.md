# 订单变更申请接入审核续办

本轮修复取消订单、修改地址的执行请求对固定措辞的依赖。语义路由已经识别出订单变更时，统一先查询订单、检查风险并创建相应类型的审核单。人工批准后使用既有续办服务实际处理，申请创建本身不修改订单。

## 证据与修改

[修改前测试](order_change_review_before.txt)显示，“这单我不买了，帮我撤掉”“收件地点换成……”等表达虽然被识别为 `cancel_order/address_change + execute`，实际只执行 `order_lookup → create_ticket`。普通工单只能认领、记录答复或结案，没有取消/改址的批准续办入口；审核服务已有该能力，却没有收到这些申请。

`routing/decision.py` 现在按已识别的执行意图要求风险检查和人工审核；查询请求不进入此分支，未取到订单仍不能继续。风险等级继续使用原规则评估，不因为必须审核就改成高风险。`response/fallback.py` 相应将审核说明调整为“复核后继续处理”。审核批准/拒绝、订单及支付状态检查、退款与消息事务均复用现有服务，没有新增自动批准或资金提交。

## 实际验证

- 未支付取消：用户申请生成 `cancel_order` 审核，订单在批准前保持原样；管理员批准后取消，不创建退款或 MQ。
- 已支付取消：SSE 请求生成审核；确认尚未发货后批准，创建一份 queued 退款及一条事件，重复批准不重复创建。
- 修改地址：SSE 请求保留用户的新地址及上下文；管理员填写核实后的地址并批准后才更新订单。
- 拒绝/状态变化：拒绝不改变订单；请求建立后订单已发货，批准改址被拒绝，不创建退款或消息。
- 权限：用户不能为其他用户的订单生成审核或工单，流程停在失败的订单查询。

这些新增测试固定语义路由结果，验证已识别请求的编排与真实数据库续办，不宣称验证了模型对所有自然语言表达的识别能力。测试中将演示订单的拣货状态改为“未发货”，以验证允许处理的业务前提；未修改原种子文件或 Dev 数据。

[最终隔离检查](release_checks_order_change_review/manifest.json)：**274 passed、11 skipped、61 subtests passed**，pytest 10.17 秒，保留 3 条已有弃用警告。专用 MySQL **108 passed、3 skipped、31 subtests passed**，测试逐项创建并清理随机库；运行器记录全量 11.235 秒、MySQL 106.570 秒。完整日志保留在同一报告目录。

## 交付与边界

[回退补丁](order_change_review.patch)相对上一阶段冻结快照，仅包含两处业务文件及新增测试；反向应用检查通过，当前源码与本轮冻结测试快照一致。

本轮补齐了已识别订单变更的审核入口。发货后变更仍需其他物流处理路径；非退款审核的重复申请合并、工作台浏览器验收、真实支付和生产接入仍未完成。没有部署或对业务订单执行操作，完整项目尚未验收完成。
