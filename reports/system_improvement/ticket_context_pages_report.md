# 工单上下文、分页与回归发现的缺陷

本阶段补齐普通工单的处理依据和旧工单入口，并修复测试实际暴露的 SQLite 客户列表错误与 MySQL 审核/撤销并发问题。原 RAG 配置、开发数据和评分规则未修改，没有运行 validation/final_test。

## 已完成

普通工单沿用人工审核的上下文作用域，在真实工具线程中保存会话 ID、最近 8 条历史消息、路由、订单快照及本轮已成功返回的政策证据。快照与后续状态修改分离，作用域结束后不带入下一次工具调用。历史未保存的内容不补造。工单提示也修正为“保存工单草稿，不修改订单”，避免原来“不会修改数据库”与实际落库行为矛盾。

`GET /tickets` 增加 `status=all|open|resolved` 和 `cursor`，保留原 `limit`、`count`、`data`，新增 `next_cursor`。用户归属及状态条件先在数据库中筛选，再分页。以创建时间及工单 ID 排序，同时间工单可完整翻页；列表上方插入新工单、上页边界记录删除不会使后页重复或漏掉已有记录。新插入的靠前记录通过刷新首页查看。这是动态列表，不是数据库快照；处理状态改变后，该记录可能移出当前筛选结果。

工作台新增状态筛选、上/下一页及刷新首页；请求序号和身份版本检查防止较早响应覆盖新列表。沿用上一阶段的认领与结案操作，管理员可查看现在实际保存的上下文和证据。

## 两项实际失败及修复

1. **SQLite 客户工单列表报错。** 新权限/分页测试报 `no such column: user_id`。原 tickets 建表和写入未包含归属列，而原 `list_visible_records` 也已经使用该列；这是此前没有覆盖的错误。现在建表、保存与 MySQL 一致，兼容迁移仅从历史 payload 的明确用户字段回填；没有归属或字段类型错误的记录不分配给客户。迁移重复执行不改变 payload，不根据订单号推测归属。
2. **MySQL 审核批准与退款撤销竞争出现 1213 死锁。** 完整日志保留在中间运行。代码检查显示撤销通过条件索引扫描加锁、批准通过主键加锁后修改状态，存在索引与行锁顺序冲突。修复为先无锁获取审核单 ID，再按顺序加主键行锁，等待后重新检查当前状态，然后继续退款和订单锁。不会把已经批准的审核记录改写为待审核撤销记录，退款撤销后迟到消息也不能恢复执行。

没有取得 InnoDB 完整锁等待图，索引冲突机制是根据 SQL 和实际竞争现象作出的诊断。另做固定时序回归：批准持有审核行时让撤销读取候选，旧实现阻塞并触发测试超时，新实现可以继续；旧实现的这个受控测试结果是阻塞超时，不冒充再次捕获的 1213。
