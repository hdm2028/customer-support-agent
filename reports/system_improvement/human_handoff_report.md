# 转人工待办与工单转派

原 `transfer_to_human` 只返回交接文字，没有落库。本阶段将它接入现有工单队列，并补齐认领人的交接路径。没有向外部客服、邮箱或消息平台发送通知，也没有改变退款执行规则。

## 实际行为

- 转人工工具保存 `pending_human_takeover` 工单，包括诉求、原因、优先级及创建时的对话、订单和政策证据。无订单号时归属于当前用户；有订单上下文时重新核查订单访问权限。客户只能查询自己的记录。
- 同一用户、订单、会话及请求 trace 的重复执行复用同一工单，保留已保存状态；新的 trace 创建新的请求。没有 trace 的独立工具调用不承诺去重，因此工具运行策略保留为不自动重试的写操作，不再将所有调用一概标记为幂等。
- 插入失败不返回已进入待办；事务中插入后故障会回滚。实际回复显示工单编号及“等待客服认领”，不会把建单说成客服已经接管。初次测试发现无订单号的模板分支提前返回泛化说明，已修复并保留初次失败记录。
- 新增 `GET /admin/operators`，仅管理员可获取已配置管理员的用户 ID，不返回访问令牌。
- 新增 `POST /admin/tickets/{ticket_id}/reassign`，接收 `target_user_id`、页面读取的 `expected_assignee` 及交接 `note`。只能转派处理中工单，目标必须是已配置管理员。状态或认领人变化时拒绝旧页面操作；相同转派重试不重复追加审计。新的认领人可以继续结案，原认领人失去结案权限。
- 工作台已增加转人工待办显示、管理员选择和交接操作。转派记录保存实际操作人、前后认领人、说明及时间，认领/结案使用同一行锁保护。

## 验证结果

|检查|结果|
|---|---|
|隔离全量|209 项测试、17 个子测试通过；9 项环境专属测试跳过|
|专用 MySQL|69 项通过；3 项 SQLite 专属测试跳过|
|前端|Node JavaScript 语法检查通过；浏览器交互尚未验收|
|固定现有路由的开发回放|工具 41/55，回答 1/4，端到端 9/12；逐案通过/失败集合均未变化|

新增测试验证无订单转人工归属及证据保存、真实工具线程传递上下文、4 线程重复提交只保存一次、新请求单独建单、插入后故障回滚、订单上下文越权、管理员目录边界、非法及陈旧转派、重复转派、转派后结案权限，以及转派与结案同时发生时只有一个操作成功。SQLite/MySQL 均实际运行这些业务检查。

固定开发回放复用 `baseline_ready` 保存的实际路由，数据及评分函数未改，未调用模型。工具结果与 baseline_ready 对比，回答和端到端与上一阶段 grounded_template_replies 对比；没有新增通过案例或退化案例。工具回放中 5 次、端到端回放中 1 次转人工成功生成工单编号，编号也出现在实际回复中；回答专项没有转人工调用。原失败仍保留，不能将回放结果称为新语义路由或真实生成质量提升。

管理员连接工作台后，在人工跟进工单列表认领待办；处理中需要交接时，填写说明、选择新的处理人并转派。被转派人必须已配置为管理员。所有操作仍为本地应用记录，不意味着外部客服平台已收到消息或人工已与用户沟通。

没有部署或修改数据库表结构。回退代码时保留已保存工单；旧版本不认识 `pending_human_takeover` 待办，应先安排人工处理，不要删除或改写历史状态。浏览器可视化验收、外部客服平台、真实支付渠道及生产身份接入仍待完成。没有运行 validation/final_test 或修改 RAG 默认方案。
