## 失败归因，不更改评分

- 语义路由唯一失败：把“这个东西我不要了”分为 return_apply，标签为 refund_apply；动作类型和实际补订单号行为通过。这是语义分类差异，无依赖故障证据。
- 工具剩余 14 个失败包含：咨询触发多余工具、缺少政策查询、投诉/取消工单链路及顺序差异、query contract 关键词不一致，以及未找到订单/拒绝退款等负向结果被记为执行不成功。详细原判定保留在 tools 报告，不能把它们全部概括为退款执行缺陷，也未重新定义通过条件。
- 模板回答 3 个失败：政策回复缺“订单”；检索文本中出现“立即到账”（需结合否定上下文理解，现有评分仍失败）；定制商品案例只查订单、未查政策。
- 端到端 3 个失败：两条回复把 MQ 等内部实现信息暴露给用户；一条退货请求只创建工单，未进入标签要求的退款/风控/人工审核链路。
- 本次正常启动基线未观察到语义路由依赖不可用。故障诊断与评分保留为独立产物，不将依赖故障自动判为业务逻辑错误。

## 一致性修复及证据

原实现退款落库与事件落库分开提交；消费时退款、订单、通知与 ack 也分开提交。新增显式事务作用域，共用同一连接，嵌套 repository context 不得提前提交，缓存更新延后到成功提交后失效。

- 创建退款与数据库 MQ 事件一起提交或回滚。
- 消费前锁定消息与退款记录；退款、订单、通知、ack 同一事务。
- 消息领取原子化；processing 租约过期可重新领取，failed 有退避和次数上限，超限进入 dead_letter。
- attempts 防止旧消费者覆盖新租约结果；完成消息不会被迟到失败改回 failed。
- 管理接口 `/refund-tasks/reconcile-events` 可补建旧 queued/待审核退款缺失的事件；已有失败事件不被误当作缺失而重复创建。未在现有业务库执行修复。
- SQLite 连接 context 退出后关闭连接，避免句柄一直滞留。

[修复前故障注入](refund_consistency_before.txt)：6 失败、1 通过。修复后已覆盖消息写入故障、首次 50 并发创建、订单/ack 故障回滚、并发重复投递、双消费者领取、租约恢复、旧消费者迟到、重试耗尽和旧孤立退款补偿。

## 权限边界

服务端 AUTH_TOKENS 映射用户与 customer/admin 角色；未配置时受保护接口返回 503，无凭据/错误凭据返回 401。订单与会话按用户归属检查，列表先按用户过滤再分页，管理接口限制管理员。旧无归属会话不能被普通用户认领。

权限 context 随工具超时线程传播；退款幂等缓存命中前仍检查订单归属。网页增加仅保留在当前页面的凭据输入，切换连接清除当前会话，普通用户不请求管理列表。未配置实际身份凭据、未重启或部署现有服务。
