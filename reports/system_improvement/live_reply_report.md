# 真实回答检查与退款结果约束（2026-09-08）

现有 Dev evaluator 已实际启用生成回答，并修复退款执行结果被模型和无关政策原文改写的问题。**最终端到端 9/12，回答专项上次实测仍为 1/4，整体回答可靠性尚未达标。**

## 运行与证据范围

隔离 runner 新增 `--live-replies`，只切换 answer/e2e 的执行入口，不改 evaluator 评分或数据。每套使用独立 SQLite、演示订单、进程内缓存和私有知识副本；本地 hash embedding、默认政策检索配置不变，两个 RAG 实验开关均关闭。支付适配器和生产身份凭据清空，所有业务写入均在副本。

复用 baseline_ready 的实际语义路由，以分离回答改动和路由波动；这不是新的实时语义路由成绩。真实模型为 glm-4-flash，温度 0.2。每次保留源码快照、trace、回复和实际用量，运行期间输入未变。[逐案核对](live_reply_comparison.json)确认全部案例的路由和最终政策 chunk ID 相同，非回答的端到端检查与数据库/MQ 副作用数量也相同。生成文本仍有随机性。

## 实际发现与修复

原回答将 MQ、幂等和重试直接展示给用户，经常漏掉引用的具体章节。通用提示增加了事实来源、完整引用与状态约束，但实测仍出现无依据的“系统显示您的退款申请正在等待审核”。提示调整没有证明能解决幻觉。

退款工具返回后，最终回复现在直接读取申请状态，区分受理、待审核、处理中、渠道成功和未知结果；同步/SSE 均不再调用模型改写。回复保留关联订单、审核单与工单信息，不再混入无关政策全文。申请受理不代表资金退回，渠道确认成功也不代表用户已收到款项。

真实链路还暴露出 `ToolExecutionError` 同时用于业务拒绝和运行异常。执行器新增 `failure_origin`，明确区分 `tool_result` 与 `runtime_exception`。回复保留“订单未支付”“已有售后”等业务原因；运行异常只报告尚未确认，避免重复提交。中间一次检查发现的误分类已修复，旧产物保留。

## 依赖、开销与测试

本次所有实际模型调用均成功返回 provider usage，没有观察到连接、超时或 API 依赖失败。004 的路由退化源于已冻结的模型输出契约错误（非法 related topic），诊断现在可识别，不能归为数据库或模型服务不可用。

端到端初始 7 次生成调用、13,006 个实际 tokens；最终 4 次生成调用、6,858 tokens，另 8 条规则回复。总耗时分别 61.86 秒和 42.55 秒，是一次运行观察，不是性能基准。回答专项最后一次为 3 次生成、2,374 tokens，另 1 条规则澄清。没有把估算用量当实际用量。

[最终隔离检查](release_checks_reply_final/manifest.json)：179 项测试、17 个子测试通过；2 项 MySQL 专用检查跳过，3 条既有框架弃用提醒。新增验证覆盖执行器归一化后的业务拒绝与运行异常、退款状态、政策文本隔离，以及开启 LLM 时同步/SSE 都不生成交易状态。

复现命令：`python -m scripts.eval.run_isolated_baseline --live-replies --route-replay-from reports/system_improvement/baseline_ready --suites answer e2e --output <新目录>`。源数据、evaluator、RAG 默认方案和原基线保留，未运行 validation、holdout、final_test。

政策咨询中的虚构状态、字段误解与引用不完整仍须解决。生成输出需要在展示前校验证据与业务状态，流式入口也不能提前暴露未校验声明。本阶段保证已有退款工具结果的确定性表达，未声称解决所有模型幻觉或完成项目。
