## 2. 本轮 rerank 代码优化

确认的缺陷：`HybridRetriever` 只复用纯语义和语义约束模式的实例，遗漏了语义融合模式；融合每次请求会由排名函数构建新实例。并发首次请求还可能重复构造对象、重复加载权重。

修改 [retriever.py](../../app/rag/retriever.py) 和 [semantic_reranker.py](../../app/rag/semantic_reranker.py)：三种语义模式统一按 retriever 实例复用；构造和首次权重加载分别加锁，加载失败仍可重试。不缓存预测分数、不改变候选、查询或排序公式。每个进程仍有自己的模型实例。

|本机真实融合模式测量|修改前|修改后|
|---|---:|---:|
|连续 3 次请求创建的模型实例|3|1|
|第 1 次请求，ms|2278.71|2302.62|
|后 2 次请求均值，ms|2548.20|713.84|
|3 次 Top5 和语义分数|与修改后相同|与修改前相同|

重复请求耗时约降低 **71.99%**。本次只测同一冻结候选的 3 次连续请求，已预热库导入和文件缓存；不是并发负载测试或服务 p95。对照推理单独记录的一次冷加载为 26.13 秒，不混入上表。详见 [生命周期测量](lifecycle_benchmark.json)。

## 3. 记忆管理实现与理由

修改 [memory.py](../../app/agent/routing/memory.py) 和 [workflow.py](../../app/agent/entry/workflow.py)：

1. **数据库为唯一状态依据。** 会话历史和待办不再从 Redis/进程缓存恢复，避免跨进程旧缓存使已删除待办复活、继续使用旧订单。代价是读取时访问数据库；历史查询使用现有索引，最多取 8 条。
2. **整轮原子保存。** 用户消息和助手回复放在同一 SQLite/MySQL 事务中；第二次写入失败，两条都回滚。故障注入已复现原实现留下半轮消息，再验证新实现没有残留。
3. **历史与待办统一过期。** 默认 1800 秒；使用数据库中的 `created_at` / `updated_at`，读取不续期。过期历史不进入执行上下文，过期待办不继续执行，因此不会通过普通历史重新继承旧退款请求。原记录仍保留，明确的新请求可以创建新待办。
4. **模型上下文有字符预算。** 默认最多 8000 字符，并保留完整最近轮次；不截断一句业务条件、不生成压缩摘要。如果最新整轮就超限，不跳过它而恢复更老的订单。当前用户消息仍正常处理，未过期的结构化 pending task 单独保留。历史查询接口仍返回原消息。

选择这个方案是先解决已复现的状态一致性和陈旧意图问题，再控制上下文规模。没有引入额外摘要模型，避免增加调用费用和摘要改写业务事实。字符预算不等于 tokenizer 实际用量；本轮未测出真实生成 token 或模型回答质量的提升。

可配置 `MEMORY_CONTEXT_MAX_CHARS`、`MEMORY_CONTEXT_TTL_SECONDS`，在进程初始化时读取；见 [.env.example](../../.env.example)。30 分钟后跨会话延续业务需要重新陈述请求。并发同一会话的整条业务请求串行化、长期用户偏好与数据保留策略不属于这次改动；整轮原子保存不能替代这些能力。

## 4. 支付沙箱与生产身份：待外部信息

实际配置检查：`PAYMENT_ADAPTER`、支付渠道标识、OIDC issuer/audience/JWKS 以及 `AUTH_TOKENS` 均未配置；`TEST_MYSQL_DSN` 已配置。没有对生产权限或真实资金进行操作。

已存在的能力包括：退款提交/查询协议、稳定退款幂等键、超时后的 `refund_unknown`、金额/币种/渠道凭证核验，以及用户订单/会话归属和管理员接口边界。这些本地能力不能算作真实渠道联调成功。

具体接入按以下顺序实施，尚未宣称完成：

|接入步骤|所需实际信息|完成证据|
|---|---|---|
|选定渠道与沙箱适配|渠道名称、沙箱配置路径、商户/应用身份、测试原支付单与本地订单映射|渠道沙箱提交结果及可查询的退款凭证|
|退款查询与对账|该渠道查询接口、原交易标识、状态与金额/币种映射|成功、失败、超时后恢复、重复请求和不匹配凭证测试；本地账与渠道记录一致|
|生产身份验证|现有身份系统、服务端可信配置及应用受众/用户映射方式|使用该系统实际签发的身份完成认证，错误身份被拒绝|
|实际权限映射|真实客户账号、审核/支付/任务管理账号及批准的权限清单|实际账号的允许/拒绝矩阵，包括跨用户订单和会话隔离|

方案理由：沿用现有支付适配边界与数据库退款状态机，让渠道差异留在适配器内；身份系统验证后映射到业务身份，再执行对象归属和接口授权。具体权限粒度需与实际岗位确认，当前 `customer/admin` 两级不能自动视为已经满足生产分权要求。

用户已被询问渠道和身份系统，仍待答复。凭据只应通过本地环境变量/配置提供，不写入此报告。未指定渠道前不随意选择支付厂商、不生成伪造的沙箱成功记录。
