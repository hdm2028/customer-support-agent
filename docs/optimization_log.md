本文档只保留中文电商智能售后客服 Agent 中最有项目价值、最适合面试展开的优化过程。每个优化点都按照“问题 -> 优化方案 -> 效果 -> 面试表达”整理，便于后续写简历和准备面试。

## 1. LangGraph 状态图编排

### 问题

早期 Agent 主流程集中在一个长函数里，路由、工具执行、上下文构造、回复生成和持久化混在一起。随着 RAG、多轮对话、安全策略、trace 和流式输出加入，线性函数会越来越难维护，也不方便展示 Agent 每一步做了什么。

### 优化方案

引入 LangGraph `StateGraph`，将 Agent 主流程拆成独立节点：

```text
load_context
-> route
-> execute_tools
-> build_model_context
-> generate_reply
-> persist_result
```

使用 `AgentWorkflowState` 作为共享状态，统一传递：

```text
user_message
conversation_id
history
pending_task
slots / missing_slots
route
tool_results
model_messages
reply
trace
result
```

每个节点只读写自己关心的字段，后续可以更容易插入条件分支、人工审核节点、重试节点或异步任务。

### 效果

- Agent 主链路从“长函数串联”升级为“可观察的状态图”。
- 路由、工具、RAG 上下文、LLM 回复和持久化边界更清楚。
- 前端执行轨迹和 trace 可以直接复用 state 中的中间结果。

### 面试表达

> 我使用 LangGraph 把 Agent 主流程拆成多个节点，通过共享 state 传递 route、slots、tool_results、model_messages 等中间状态。这样 Router、Tool Executor、Prompt 构造和持久化解耦，后续插入人工审核、条件分支或失败重试会更容易。

## 2. RAG 检索质量与 Evidence Context 优化

### 问题

售后客服回答不能只靠模型通用知识。退货、保修、物流异常、发票、会员权益等问题必须基于平台政策文档。如果 RAG 召回错误，或者模型没有引用证据，就容易产生无依据回答。

早期 RAG 还存在一个典型问题：能命中文档，但不一定命中正确章节。例如修改地址问题，容易命中同一份文档里的“已发货订单修改”，但真正需要的是“修改收货地址”条款。

### 优化方案

RAG 侧做了四层优化：

- 文档解析：支持 Markdown、TXT、PDF。
- Chunk 切分：按章节标题切分，保留 `source`、`section`、`page`、`citation`。
- 混合检索：智谱 `embedding-3` 向量相似度 + 业务关键词召回。
- Query enrichment：把用户问题、订单状态、物流状态、商品名称、订单备注和业务意图一起拼入检索 query。

模型上下文不直接塞原始工具 JSON，而是整理成 evidence context：

```text
[订单信息]
订单号、商品名称、订单状态、物流状态、签收日期、备注

[售后政策证据]
来源、章节、相关分数、政策正文、citation

[工单信息]
工单状态、风险提示、关联订单、问题类型、下一步
```

Prompt 中要求模型：

- 使用政策时必须引用 citation。
- 证据不足时必须说明资料不足。
- 不允许编造工具结果中不存在的信息。

### 效果

当前 RAG 评估：

```text
RAG eval: 8/8
Top1 来源命中率: 1.0
Top3 来源命中率: 1.0
关键词命中率: 1.0
```

当前回答评估：

```text
Answer eval: 21/21
Citation 通过率: 1.0
风险控制通过率: 1.0
```

### 面试表达

> 我没有只做向量检索，而是做了带 citation 的 evidence context。文档按章节切分，chunk 保留 source、section、page 和 citation；检索时结合 embedding 相似度和业务关键词，并用订单状态、物流状态、商品信息做 query enrichment。最终回答必须引用本轮检索到的 citation，证据不足时不能编造。

## 3. 多轮槽位补全

### 问题

真实售后任务经常不是单轮就能完成。例如修改收货地址至少需要：

```text
order_id
new_address
```

如果用户只说“帮我改收货地址”，系统直接创建工单会导致工单信息不完整，人工客服仍然需要二次追问。

### 优化方案

新增 pending task 机制，保存当前会话中待补全的业务任务：

```text
required_slots: 当前任务需要哪些槽位
slots: 已经收集到哪些槽位
missing_slots: 还缺哪些槽位
user_request: 原始用户诉求
```

示例：

```text
用户：帮我改收货地址。
Agent：请提供订单号和新的收货地址。

用户：10009
Agent：订单号已收到，请继续提供新的收货地址。

用户：新地址是北京市朝阳区望京街道88号
Agent：查询订单、检索政策、创建待人工审核的地址修改工单。
```

### 效果

`scripts/multi_turn_smoke_test.py` 通过，多轮补齐槽位后才会继续执行工具：

```text
第三轮工具:
order_lookup -> policy_search -> create_ticket
```

### 面试表达

> 我实现了 pending task 和多槽位补全。对修改地址这类任务，系统会保存当前会话缺失的 `order_id` 和 `new_address`，用户下一轮补充后再合并成完整任务输入。这样可以避免信息不完整时过早创建工单。

## 4. 高风险动作与订单优先策略

### 问题

客服 Agent 涉及退款、赔付、取消订单、修改地址等高风险动作，不能让模型直接承诺“已经退款”或“已经修改地址”。另外，售后判断强依赖订单上下文，用户只说“我的手表坏了”时，系统不能直接判断是否在保修期内。

### 优化方案

在 Router 和 fallback 层增加确定性控制：

- 高风险动作必须提示人工审核。
- 提示词注入直接拒绝。
- 缺少订单号时先追问订单号。
- 信息不足或高风险场景强制走规则兜底，不调用真实 LLM 自由生成。

订单优先规则覆盖：

```text
保修 / 维修 / 检测
坏了 / 故障 / 质量问题
退款 / 退货 / 赔付
物流 / 发货 / 签收
发票 / 投诉 / 缺货
```

示例：

```text
用户：我的手表坏了
Agent：请您提供订单号，我才能继续查询订单状态并判断售后方案。
```

### 效果

避免模型在无订单上下文时判断：

- 是否在保修期内
- 是否能退款
- 是否物流异常
- 是否可以修改地址

### 面试表达

> 我没有把安全完全交给 prompt，而是在工作流控制层做了确定性兜底。只要涉及退款、赔付、取消订单、修改地址或缺少订单号的售后判断，就不会让模型自由生成，而是先追问信息或转人工审核。

## 5. 订单查询失败短路与工单资格判断

### 问题

Router 只能判断“理论上需要哪些工具”，但真正能不能继续执行，要看工具结果。

典型错误：

```text
用户：订单 10025 手表坏了，还在保修期内吗？
```

`order_lookup` 已经返回“未找到订单号”，但系统仍继续 `policy_search` 和 `create_ticket`，最终可能生成“已创建保修检测工单”的错误回复。

另一个问题是，只要 Router 命中工单意图，系统就会创建工单。真实业务里，物流刚更新未超过 48 小时，或者订单尚未签收，都不应该直接建异常/保修工单。

### 优化方案

新增两层执行期校验：

第一层：订单查询失败短路。

```text
order_lookup 失败
-> 停止 policy_search
-> 停止 create_ticket
-> 强制规则回复
```

第二层：工单资格判断。

新增 `app/agent/ticket_policy.py`，在创建工单前判断：

- 订单不存在：不创建工单。
- 订单未签收：不创建保修检测工单。
- 物流更新未超过 48 小时：不创建物流异常工单。
- 超过保修期：不直接创建保修工单，提示人工确认。
- 退款、投诉、地址修改等高风险动作：只创建待人工审核工单。

不满足创建条件时返回 `ticket_decision`：

```text
工具结果：ticket_decision
是否创建工单：否
原因：订单尚未签收，暂时不能创建保修检测工单
```

### 效果

新增评估样例：

```text
订单 10025 手表坏了，还在保修期内吗？
订单 10011 物流刚刚更新但我觉得太慢了，能创建物流异常工单吗？
订单 10002 手环坏了，还能创建保修检测工单吗？
```

当前工具评估：

```text
Agent eval: 21/21
```

### 面试表达

> 我将 Router 的“工具计划”和 Executor 的“业务可执行性”分开。Router 可以判断用户可能需要工单，但真正创建工单前会先查订单，再根据订单是否存在、是否签收、物流更新时间和保修期做二次校验。不满足条件时返回 `ticket_decision`，避免对不存在或不满足条件的订单生成虚假工单。

## 6. 可观测性、流式输出与前端执行轨迹

### 问题

Agent 回答慢或回答错误时，如果只有最终回复，很难判断问题出在哪里：

```text
是 Router 错了？
是订单查错了？
是 RAG 没召回？
是 LLM 响应慢？
还是持久化慢？
```

早期前端也主要展示原始 JSON，业务人员或面试官不容易看懂 Agent 为什么这么回答。

### 优化方案

后端 trace 记录：

- `route`
- `tool_results`
- `model_context`
- `reply`
- `timings`

SSE 流式接口分阶段推送：

```text
route
tool_result
execution_blocked / ticket_decision
token / message
timing
done
```

前端将原始 JSON 转换为业务可读摘要：

- 路由判断：展示订单号、风险等级、计划调用工具。
- 订单查询：展示订单状态、物流状态、签收日期。
- 政策检索：展示命中的 citation 和相关分数。
- 工单结果：展示工单状态、问题类型和下一步。
- 工单判断：展示为什么创建或不创建工单。
- 性能耗时：左侧展示各节点耗时和总耗时。

### 效果

- 用户能更早看到 Agent 执行进度。
- 面试演示时可以直观看到 Agent 的“判断 -> 工具 -> 证据 -> 回复”全过程。
- 慢请求可以通过 trace 分析定位到 RAG、LLM、数据库或平台冷启动。

### 面试表达

> 我为 Agent 增加了基础可观测性。每次请求都会记录路由、工具结果、模型上下文、回复模式和节点耗时，前端通过 SSE 展示路由、工具结果、工单判断和最终回复。这样项目不只是能回答，还能解释自己每一步为什么这样做。

## 项目总结

这个项目的核心价值不在于“接了一个大模型 API”，而在于把中文电商售后客服拆成了可控的工程流程：

```text
意图路由
-> 订单查询
-> 政策检索
-> 业务资格判断
-> 工单草稿
-> 风险控制
-> 可追踪回复
-> 评估回归
```

可以放入简历的浓缩表述：

```text
中文电商智能售后客服 Agent：基于 FastAPI、LangGraph、RAG、SQLite 和智谱大模型构建，支持订单查询、售后政策检索、工单草稿、多轮槽位补全、流式输出和自动化评估。使用 LangGraph StateGraph 编排 Agent 主链路，通过 Router、Tool Executor、Evidence Context 和 Ticket Policy 解耦复杂售后流程；构建 Router/RAG/Answer 三层评估，当前路由工具评估 21/21、RAG 评估 8/8、回答质量评估 21/21；针对退款、赔付、修改地址等高风险动作实现人工审核兜底，并通过订单查询失败短路和工单资格判断避免生成虚假业务结果。
```
